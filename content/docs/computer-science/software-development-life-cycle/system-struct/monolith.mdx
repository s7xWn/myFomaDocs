title: Монолит
---

Монолитная архитектура — это способ построения приложения, при котором вся основная логика находится в одном приложении и разворачивается как единое целое.

<Callout>

Монолит ≠ плохая архитектура.

Подходит для **pet проектов** и **стартапов**.

</Callout>

Монолит — это прежде всего когда backend-приложение представляет собой единый разворачиваемый блок.

Это действительно может быть монолитная система:

```
    Один сервер
┌──────────────────────────────┐
│ Frontend                     │
│ Backend (монолит)            │
│ Database                     │
└──────────────────────────────┘
```

Но можно сделать так:

```
Frontend ──→ Backend ──→ Database
   │            │            │
Server 1     Server 2      Server 3
```

И backend всё равно может оставаться монолитом, несмотря на то что компоненты находятся на разных серверах.

<Callout title="Фраза неправильная:" type="error">

> Frontend + Backend + БД на одном сервере = монолит

</Callout>

<hr />

## Положительные стороны

Монолит часто очень удобен на старте проекта:

- проще разработать (запустить, отладить, протестировать) => один deployment
  - весь код в одном месте
  - БД общая

<hr />

## Отрицательные стороны

Проблемы начинают проявляться, когда приложение становится очень большим.

- Долгая сборка проекта
- Масштабирование (пределы его)
  - Нельзя независимо масштабировать части (например нужно увеличить мощность определённого модуля)
- Падение. Если что-то падает, то падает всё приложение
  - Если ошибка в аппаратной части, то падает только 1 сервер
  - Если в коде, то все сервера.
- Сложнее изменять большой проект <br/> _Со временем кодовая база становится большой, и разработчику сложнее понять, что на что влияет._

<hr />

## Вертикальное масштабирование

Вертикальное масштабирование (Vertical Scaling) — это когда мы усиливаем один сервер, вместо того чтобы добавлять новые серверы.

> Мы добавляем мощность существующей машины (CPU,GPU,RAM,Disk space)

<Callout type="warn">
  Но у вертикального масштабирования есть физический предел: нельзя бесконечно
  увеличивать CPU и RAM одного сервера.
</Callout>

<hr />

## Горизонтальное масштабирование

Горизонтальное масштабирование (Horizontal Scaling) - это когда мы добавляем новые серверы/экземпляры приложения, чтобы распределить нагрузку между ними.

<Callout title="Важный момент:" type="success">

Горизонтально масштабировать можно и монолит. Не обязательно переходить на микросервисы.

</Callout>

1. Перед ними ставим Load Balancer
   - <Callout type="warn"> Но все сервера стучатся к одной базе => нагрузка на БД растёт, и в какой-то момент она становится bottleneck: не хватает ресурсов, растёт latency и запросы начинают выполняться медленнее. </Callout>
   - <Callout> Большенстве запросов к БД - это чтение => (2) Пункт </Callout>
2. Создаём реплики БД, из которых выполняются операции чтения (Это позволяет разгрузить основную БД)
   - Записи по-прежнему идут в основную БД
   - Чтение распределяем между репликами
3. Самые часто запрашиваемые данные выносим в кеш (Например, Redis)
   - Если данные есть в кеше, запрос вообще не доходит до БД
   - Чем выше cache hit rate, тем сильнее снижается нагрузка на БД
4. Всё, что не обязательно делать прямо во время запроса, уносим в фон (Для этого обычно используют связку Message Broker / Queue + Workers, наример RabbitMQ. )
   - Заводим очередь задач — список работ, которые нужно выполнить
   - Приложение быстро добавляет задачу в очередь и отвечает пользователю
   - Воркеры забирают задачи из очереди и выполняют их в фоне
   - При необходимости добавляем больше воркеров → горизонтально масштабируем обработку

### Плюсы

- Лучшее отказоустойчивость

## Модульный монолит

Модульный монолит — это одно приложение, которое разделено внутри на независимые модули по бизнес-доменам.

То есть технически мы всё ещё имеем один deployable application, одну кодовую базу и обычно один процесс/набор одинаковых инстансов, но внутри код не превращён в огромную «кашу».

<Callout title="Главная идея:" type="success">

Получить преимущества хорошей структуры микросервисов, не платя пока за сложность распределённой системы.

</Callout>

<details>
  <summary>Главное отличие от обычного монолита</summary>

Обычный монолит:

```
Orders ─────┐
Users ──────┼──► всё связано со всем
Payments ───┤
Products ───┘
```

Модульный монолит:

```
Users ──────► Users Module
                   │
Orders ─────► Orders Module
                   │
Payments ───► Payments Module
```

Модули стараются общаться через чётко определённые интерфейсы, а не напрямую лазить во внутренности друг друга.

</details>
