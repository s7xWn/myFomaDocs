title: Микросервисы
---

Микросервисная архитектура — это способ построения приложения, при котором система разделена на несколько небольших автономных сервисов, каждый из которых отвечает за отдельную бизнес-функцию.

<Callout>

В классической микросервисной архитектуре есть принцип: каждый микросервис владеет своими данными.

> У каждого микросервиса должна быть своя граница владения данными.

</Callout>

Каждый микросервис обычно:

- имеет свою ответственность;
- может независимо разворачиваться;
- может независимо масштабироваться;
- может разрабатываться и изменяться отдельно;
- взаимодействует с другими сервисами через сеть.

<Callout title="Главная идея:" type="success">
  Разделение приложения на независимые бизнес-сервисы, а не физическое
  размещение компонентов на разных машинах.
</Callout>

<hr />

## Положительные стороны

- Быстрая сборка проекта
- Масштабирование
  - Можно независимо масштабировать части (например нужно увеличить мощность определённого сервиса)
- Отказоустойчивость. Если что-то падает, то падает только один микросервис
- Проще изменять большой проект, т.к. каждая команда отвечает за свой микросервис

<hr />

## Отрицательные стороны

- Большая инфраструктура, в которой каждый сервис требует развёртывание
  - Решение: Docker, Kuber, CI/CD, monitroing

## База данных

Если два сервиса постоянно ходят в таблицы друг друга, это часто сигнал, что границы микросервисов выбраны неудачно.

### Вариант 1 — отдельная БД

```
User Service    → PostgreSQL #1
Order Service   → PostgreSQL #2
Payment Service → PostgreSQL #3
```

### Вариант 2 — один PostgreSQL, разные базы

```
              PostgreSQL
             /    |     \
            /     |      \
       users_db orders_db payments_db
           ↑        ↑        ↑
         User     Order    Payment
       Service   Service   Service
```

### Вариант 3 — одна БД, разные схемы

```
             PostgreSQL
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    users      orders     payments
    schema     schema      schema
       ↑          ↑          ↑
     User       Order      Payment
    Service    Service    Service
```

### Плохая практика

```
User Service ──────┐
Order Service ─────┼──► Одна общая БД
Payment Service ───┘
```

## API Gateway

API Gateway — это единая точка входа в систему для внешних клиентов: frontend, мобильного приложения, других внешних систем.

Без API Gateway:

```
Frontend ──► User Service
Frontend ──► Order Service
Frontend ──► Payment Service
Frontend ──► Product Service
```

С API Gateway:

```
                         ┌──► User Service
                         │
Frontend ──► API Gateway ├──► Order Service
                         │
                         ├──► Payment Service
                         │
                         └──► Product Service
```

### Зачем он нужен?

- Без Gateway приложению пришлось бы знать адреса всех сервисов.
- Защиита от атаки сервисов
  - DDOS

<hr />

Gateway может делать гораздо больше:

- Маршрутизация — определить, какому сервису передать запрос.
- Авторизация — проверить JWT/token.
- Authentication — определить, кто пользователь.
- Rate limiting — ограничить количество запросов.
- Logging — записывать запросы.
- CORS — управлять доступом браузера.
- TLS termination — принимать HTTPS.
- Load balancing — распределять запросы между экземплярами сервиса.
- Aggregation — собрать данные от нескольких сервисов в один ответ.

## Общение микросервисов

### Синхронное взаимодействие

Один сервис отправляет запрос и ждёт ответ.

- REST API
- gRPC

#### Минусы:

- Зависимость от цепочки взаимодействия микросервисов.

<hr />

### Асинхронное взаимодействие (события)

Сервис отправляет сообщение в брокер сообщений, а другой сервис забирает его позже.

- Kafka — потоковые события, высокая пропускная способность.
- RabbitMQ — очереди сообщений, маршрутизация.
- NATS — лёгкий и быстрый messaging.
- AWS SQS/SNS, Google Pub/Sub и т. п.
