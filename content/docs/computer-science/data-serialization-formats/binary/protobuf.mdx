Protocol Buffers (Protobuf) — это разработанный Google формат сериализации данных,
который позволяет эффективно преобразовывать структурированные данные в компактный бинарный формат для хранения и передачи по сети.

Protobuf — это способ упаковать данные так, чтобы они занимали меньше места и быстрее передавались между программами.

Основные сценарии использования:

1. [**gRPC**](../../architectural-style-web-api/grpc.mdx) — Protobuf часто используется как формат обмена данными между микросервисами.
2. **Микросервисная архитектура** — эффективная передача сообщений между сервисами.
3. **Backend-разработка** — сериализация объектов для сетевого взаимодействия.
4. **Хранение данных** — сохранение структурированных данных в бинарном виде.
5. **Мобильные приложения** — уменьшение объёма передаваемых данных.

<hr />

## Как работает Protobuf

В Protobuf сначала описывается структура данных в специальном файле `.proto`.<br/>
На основании `.proto` генерируется код для разных языков программирования: Java, Python, Go, C++, C#, JavaScript и других.<br/>
Затем этот код позволяет сериализовать и десериализовать данные.

Принцип работы:

```
          Объект
    (id = 123, name = Ivan)
            ||
        Serialization
            ||
            \/
    Бинарные данные Protobuf
    (Компактный набор байтов)
            ||
    Передача по сети
            ||
            \/
    Объект на стороне получателя
-----------------------------------
Получатель использует ту же схему или совместимую с ней версию.
```

<details>
  <summary>Пример</summary>

Представим, что у нас есть пользователь:

```json
{
  "id": 123,
  "name": "Ivan",
  "email": "ivan@example.com"
}
```

- В JSON данные передаются в текстовом виде.
- В Protobuf сначала описывается структура данных в специальном файле `.proto`.

```protobuf
syntax = "proto3";

message User {
    int32 id = 1;
    string name = 2;
    string email = 3;
}
```

- `message User` — описание структуры пользователя.
- `int32` — целое число.
- `string` — строка.
- `id`, `name`, `email` — названия полей.
- `1`, `2`, `3` — уникальные номера полей (field numbers).

</details>

<hr />

## Важная особенность: обратная совместимость

Protobuf позволяет развивать API, не ломая старых клиентов, если соблюдать правила изменения схемы.

Например, можно добавить новое поле. <br/>
Старые клиенты смогут продолжать читать известные им поля, игнорируя неизвестные.

<Callout title="Важно" type="warn">
  Номера уже использованных полей нельзя повторно присваивать другим полям.
  Удалённые номера желательно объявлять через `reserved`.
</Callout>

## Структура `.proto`

Типичный `.proto` файл выглядит так:

```protobuf
syntax = "proto3";

package users;

option go_package = "myapp/gen/users";

import "google/protobuf/timestamp.proto";

// Описание структур
message User {
    // ...
}

// Описание сервиса
service UserService {
    // ...
}
```

### `message` — описывает структуру данных

`message` — основная конструкция Protobuf.

```protobuf
message Name {
    dataType varName = 1;
}
```

- `Name` — название структуры
- [`dataType`](#data-types) — тип данных
- `varName` — название переменной
- `1` — field numbers.

#### field number

- Номера должны быть уникальными внутри одного `message`.
- Нельзя менять номер поля, если оно уже используется.
- Нельзя повторно использовать номер удалённого поля.
- Номера от 1 до 15 занимают меньше места при кодировании, поэтому их выгодно отдавать часто используемым полям.
- Диапазон 19000–19999 зарезервирован самим Protobuf.

#### Вложенные `message`

Один `message` может содержать другой `message`.

<details>
  <summary>Пример</summary>
  
Пользователь имеет адрес:

```protobuf
message Address {
    string country = 1;
    string city = 2;
    string street = 3;
}

message User {
    int64 id = 1;
    string name = 2;
    Address address = 3;
}
```

<details>
  <summary>Go:</summary>

```go
user := &pb.User{
    Id:   1,
    Name: "Alex",
    Address: &pb.Address{
        Country: "Latvia",
        City:    "Riga",
        Street:  "Brivibas",
    },
}
```

</details>

### `enum` — перечисления

```protobuf
enum NameEnum {
    VALUE_UNSPECIFIED = 0;
    ...
}
```

```protobuf
message NameMessage {
    NameEnum field_name = field_number;
}
```

В `proto3` значение `enum` по умолчанию — **нулевое**. Поэтому лучше явно предусмотреть состояние `UNSPECIFIED`, чтобы не путать отсутствие явно заданного статуса с активным пользователем.

| Go                           |
| ---------------------------- |
| `field_name: pb.VALUE_ENUM,` |

### Типы данных [#data-types]

Разница между `int32`, `sint32` и `fixed32`.

- `int32` использует Varint-кодирование.
- `sint32` использует ZigZag-кодирование, которое эффективнее для небольших отрицательных чисел.
- `fixed32` всегда занимает 4 байта для значения.

#### `oneof` — только одно значение из нескольких

```protobuf
message NameMessage {
    oneof NameVar {
        value_type field_name = field_number;
        ...
    }
}
```

<details>
  <summary>Пример</summary>

Представим, что пользователь может авторизоваться через:

- Email;
- Телефон;
- Google ID.

При этом одновременно должен использоваться только один способ.

```protobuf
message AuthMethod {
    oneof method {
        string email = 1;
        string phone = 2;
        string google_id = 3;
    }
}
```

<details>
  <summary>Go:</summary>

```go
auth := &pb.AuthMethod{
    Method: &pb.AuthMethod_Email{
        Email: "alex@example.com",
    },
}
```

</details>

#### `optional` — необязательные поля

```protobuf
optional value_type field_name = field_number;
```

В `proto3` обычные скалярные поля имеют значения по умолчанию. <br/>
Например: Если значение для поля не задано, при чтении ты получишь `0`.

Но иногда важно различать:

- Пользователь не указал значение.
- Пользователь указал `0`.

Для этого используется `optional`.

## Сравнение с другими форматами сериализации данных

### JSON

| Характеристика   | Protobuf                 | JSON            |
| ---------------- | ------------------------ | --------------- |
| Формат           | Бинарный                 | Текстовый       |
| Размер           | Обычно меньше            | Обычно больше   |
| Скорость         | Обычно быстрее           | Часто медленнее |
| Читаемость       | Низкая без декодирования | Высокая         |
| Схема данных     | `.proto`                 | Не обязательна  |
| Поддержка языков | Много языков             | Практически все |

JSON хранит названия полей непосредственно в сообщении:

```json
{ "id": 123, "name": "Ivan" }
```

Protobuf вместо названий полей использует их числовые идентификаторы, что позволяет экономить место.
