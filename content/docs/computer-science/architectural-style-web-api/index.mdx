## gRPC vs REST

**REST** и **gRPC** — подходы к взаимодействию между приложениями и сервисами.

- **REST** обычно использует HTTP и JSON. Это простой и естественный вариант для браузерных приложений, публичных API и CRUD-сценариев.
- **gRPC** использует RPC-модель, обычно HTTP/2 и Protocol Buffers (Protobuf). Он особенно полезен для взаимодействия между backend-сервисами, строгих контрактов и потоковой передачи данных.

Это не взаимоисключающие технологии: в одной системе можно использовать обе.

| Критерий               | REST                              | gRPC                                              |
| ---------------------- | --------------------------------- | ------------------------------------------------- |
| Модель взаимодействия  | Ресурсы и HTTP-методы             | Вызовы методов сервиса (RPC)                      |
| Типичный формат данных | JSON                              | Protobuf                                          |
| Транспорт              | Обычно HTTP/1.1 или HTTP/2        | Обычно HTTP/2                                     |
| Описание контракта     | Часто OpenAPI                     | `.proto`                                          |
| Генерация клиентов     | Возможна через OpenAPI            | Типичный сценарий через Protobuf                  |
| Поддержка браузером    | Нативная                          | Обычный gRPC напрямую браузером не поддерживается |
| Streaming              | Обычно SSE или WebSocket          | Встроенные виды streaming                         |
| Отладка                | Просто читать HTTP-запросы и JSON | Часто нужны специальные инструменты               |
| Типичные сценарии      | Web API, публичные API, CRUD      | Микросервисы, RPC, streaming                      |

### Когда выбирать REST

REST — хороший выбор, если:

- frontend написан на React или другом браузерном фреймворке;
- приложение в основном выполняет CRUD-операции;
- нужен публичный API для внешних клиентов;
- важны простая интеграция, отладка и совместимость с браузерами;
- полезны стандартные HTTP-механизмы: кеширование, прокси, CDN и HTTP-коды статусов.

Пример API:

```http
GET    /api/products
GET    /api/products/123
POST   /api/orders
PATCH  /api/users/me
DELETE /api/cart/items/123
```

React может обращаться к такому API через `fetch`, `axios` или TanStack Query.

### Когда выбирать gRPC

gRPC стоит рассматривать, если:

- backend состоит из микросервисов, которым нужно часто обмениваться данными;
- нужны строгие контракты и генерация клиентов из `.proto`;
- важны компактная сериализация и эффективная передача сообщений;
- нужен streaming между сервисами;
- разные сервисы написаны на разных языках, но должны использовать общий контракт.

Основные виды вызовов gRPC:

| Вид                     | Что происходит              |
| ----------------------- | --------------------------- |
| Unary                   | Один запрос → один ответ    |
| Server streaming        | Один запрос → поток ответов |
| Client streaming        | Поток запросов → один ответ |
| Bidirectional streaming | Двунаправленный поток       |

**Важно:** gRPC не гарантирует автоматического ускорения системы. На производительность также влияют сеть, число запросов, размер данных, кеширование и реализация сервисов.

### React и gRPC: ограничение браузера

Браузер не поддерживает обычный gRPC-клиент напрямую. Для RPC-взаимодействия из React используют специальные решения.

#### gRPC-Web

gRPC-Web позволяет браузеру вызывать gRPC-сервисы через специальный браузерный протокол.

Типичная схема:

```text
React
  |
  | gRPC-Web
  v
Envoy Proxy
  |
  | обычный gRPC
  v
gRPC Backend
```

Часто используется proxy, например Envoy, который преобразует запросы gRPC-Web в обычный gRPC.

#### Connect

Connect — RPC-фреймворк и протокол из экосистемы Buf. Для TypeScript существует клиентская библиотека Connect-ES.

Connect поддерживает:

- Connect protocol;
- gRPC;
- gRPC-Web.

Отдельный Envoy обычно не нужен, если backend сам поддерживает Connect.

Пример клиента Connect в TypeScript:

```typescript
import { createClient } from "@connectrpc/connect";
import { createConnectTransport } from "@connectrpc/connect-web";

import { UserService } from "./gen/users_pb";

const transport = createConnectTransport({
  baseUrl: "https://api.example.com",
});

const client = createClient(UserService, transport);

const user = await client.getUser({ id: 123 });

console.log(user.name);
```

И gRPC-Web, и Connect позволяют генерировать типизированные TypeScript-клиенты из Protobuf-контрактов.

### Рекомендуемая гибридная архитектура

Для React-приложения с backend на микросервисах часто удобно разделить коммуникацию:

```text
                  React
                    |
                REST / JSON
                    |
                API Gateway
                    |
              ---------------
              |      |      |
             gRPC   gRPC   gRPC
              |      |      |
            Users  Orders Payments
            Service Service Service
```

Рекомендации:

- **React ↔ API Gateway:** REST/JSON — простой и естественный вариант для браузера.
- **API Gateway ↔ микросервисы:** gRPC, если нужны RPC-контракты и эффективная внутренняя коммуникация.
- **Микросервис ↔ микросервис:** gRPC, если он соответствует требованиям системы.
- **Real-time обновления в браузере:** SSE или WebSocket; выбор зависит от того, нужен ли только поток событий от сервера или двунаправленный обмен.
- **React ↔ RPC backend:** Connect или gRPC-Web, если frontend должен непосредственно использовать Protobuf/RPC-контракты.

### Практическая рекомендация

Для нового проекта разумно начать со следующего:

1. Использовать **REST** между React и backend.
2. Описывать REST API через **OpenAPI** и при необходимости генерировать TypeScript-клиент.
3. Использовать **gRPC** для внутренних вызовов между микросервисами, если это оправдано требованиями.
4. Для streaming выбирать технологию по сценарию: gRPC внутри backend, SSE для односторонних событий в браузере, WebSocket для двунаправленного обмена.
5. Рассматривать **Connect** или **gRPC-Web**, если frontend должен работать непосредственно с Protobuf/RPC-контрактами.

### Итог

- **REST** — практичный выбор по умолчанию для React ↔ Backend.
- **gRPC** — сильный вариант для Backend ↔ Backend, особенно в микросервисной архитектуре.
- **Connect и gRPC-Web** позволяют использовать RPC-подход и Protobuf-контракты из браузера, но добавляют технологические и инфраструктурные решения, которые нужны не каждому проекту.

Не стоит выбирать gRPC только ради предполагаемой скорости. Выбирай его, когда нужны его конкретные преимущества: строгие контракты, генерация клиентов, streaming или особенности внутренней коммуникации.
