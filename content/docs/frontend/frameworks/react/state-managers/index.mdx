---
title: State managers
---

— это конкретный инструмент/библиотека, которая реализует **state management**.

:::note
**State manager'ы** позволяют хранить и изменять состояние приложения
независимо от структуры и жизненного цикла отдельных UI-компонентов,
обеспечивая централизованный доступ к данным и их синхронизацию между разными частями интерфейса.
:::

State manager'ы нужны для управления состоянием приложения, особенно когда это состояние:

<details>

<summary>используется несколькими частями интерфейса; </summary>

Означает, что одно и то же состояние нужно одновременно разным частям UI, и они должны его читать и/или менять синхронно.

Допустим, есть состояние: пользователь авторизован. И его используют разные части интерфейса:

- страница профиля
- верхнее меню (показывает имя пользователя)
- кнопка “Выйти”

Если хранить состояние локально в каждом компоненте, возникает проблема: <br/>
если пользователь изменился (вошёл/вышел), нужно обновить ВСЕ места вручную.

Что происходит с state manager’ом <br/>
Есть одно общее состояние, и все части UI просто подписаны на него:

```
Header → читает AuthStore
Profile → читает AuthStore
Cart → читает AuthStore
```

</details>

<details>

<summary>
  должно сохраняться независимо от жизненного цикла отдельных
  виджетов/компонентов;
</summary>

Состояние не должно исчезать, когда UI-компонент уничтожается или пересоздаётся. <br/>
Если состояние хранится внутри компонента, оно живёт ровно столько, сколько живёт сам компонент.

  </details>

<details>

<summary>требует централизованной логики обновления;</summary>

Под централизованной логикой обновления понимается ситуация, когда правила
изменения состояния находятся в одном месте, а не разбросаны по всему
приложению.

Например, есть состояние корзины интернет-магазина.

```
Экран товара:
    сам добавляет товары в корзину

Экран корзины:
    сам пересчитывает итоговую сумму

Экран скидок:
    сам применяет скидки

Экран оформления:
    сам проверяет наличие товаров
```

**Логика изменения корзины оказывается размазана по нескольким экранам. Если правила изменятся, придется искать и менять код во многих местах.**

С централизованным state manager:

```
CartStore
  addItem()
  removeItem()
  applyDiscount()
  calculateTotal()

  Экран товара -> вызывает addItem()
  Экран корзины -> читает состояние
  Экран скидок -> вызывает applyDiscount()
  Экран оформления -> читает состояние
```

Теперь все изменения проходят через CartStore, а UI только отображает данные и отправляет команды.

  </details>

<details>

<summary>
  должно быть доступно из разных мест приложения без передачи через множество
  уровней компонентов.
</summary>

Prop Drilling

  </details>
