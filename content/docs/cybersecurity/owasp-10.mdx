OWASP Top 10 — это список десяти наиболее распространённых и опасных угроз безопасности веб-приложений.

OWASP расшифровывается как Open Worldwide Application Security Project — международная некоммерческая организация, которая занимается повышением безопасности программного обеспечения.

Проще говоря, OWASP Top 10 — это своего рода базовый стандарт знаний по кибербезопасности для разработчиков, тестировщиков и специалистов по информационной безопасности.

### A01. Broken Access Control — нарушение контроля доступа

**Суть:** пользователь получает доступ к данным или функциям, которые ему не принадлежат.

<details>
  <summary>Пример</summary>

Есть два пользователя:

- User A: `/api/users/100`
- User B: `/api/users/200`

User A меняет ID `100` на `200` и получает чужие данные.

Это называется **IDOR (Insecure Direct Object Reference)**, один из распространённых вариантов нарушения контроля доступа.

</details>

Как защищаться:

- Проверять права доступа на сервере при каждом запросе.
- Проверять, принадлежит ли объект текущему пользователю.
- Не полагаться на скрытые кнопки и ограничения frontend.
- Использовать RBAC (Role-Based Access Control).
- Запрещать доступ по умолчанию.

Что проверять тестировщику:

- Может ли обычный пользователь открыть данные администратора?
- Может ли пользователь A получить данные пользователя B?
- Можно ли вызвать административный API без соответствующих прав?
- Работают ли ограничения доступа не только в UI, но и в API?

### A02. Security Misconfiguration — неправильная настройка безопасности

**Суть:** сервер, приложение или инфраструктура настроены небезопасно.

Примеры:

- Включён Debug Mode на production.
- Открыта административная панель.
- Используются стандартные пароли.
- Сервер раскрывает подробности ошибок.
- Неправильно настроены CORS или HTTP Security Headers.

Как защищаться:

- Отключать Debug Mode на production.
- Удалять стандартные пароли.
- Ограничивать доступ к административным интерфейсам.
- Настраивать HTTPS.
- Использовать безопасные HTTP-заголовки.
- Регулярно проверять конфигурацию сервера.

Что проверять:

- Не отображаются ли Stack Trace и внутренние ошибки?
- Нет ли открытых административных страниц?
- Настроены ли Security Headers?
- Не разрешён ли CORS для любых источников без необходимости?

### A03. Software Supply Chain Failures — уязвимости цепочки поставки ПО

**Суть:** приложение использует скомпрометированные или уязвимые библиотеки, пакеты, инструменты сборки и сторонние компоненты.

<details>
  <summary>Пример</summary>

Разработчик подключает стороннюю библиотеку с известной критической уязвимостью. Злоумышленник использует её для атаки на приложение.

</details>

Как защищаться:

- Использовать проверенные библиотеки.
- Регулярно обновлять зависимости.
- Проверять зависимости через SCA (Software Composition Analysis).
- Использовать lock-файлы.
- Проверять целостность пакетов.
- Ограничивать доступ к CI/CD.

Что проверять:

- Есть ли зависимости с известными CVE?
- Используются ли устаревшие библиотеки?
- Проверяются ли пакеты перед сборкой?

### A04. Cryptographic Failures — ошибки криптографии

**Суть:** конфиденциальные данные недостаточно защищены.

Примеры:

- Пароли хранятся в открытом виде.
- Используется слабое шифрование.
- Данные передаются через HTTP.
- Секретные ключи хранятся прямо в исходном коде.

Как защищаться:

- Использовать HTTPS/TLS.
- Хранить пароли с помощью Argon2id, bcrypt или scrypt.
- Использовать современные криптографические алгоритмы.
- Не хранить секреты в исходном коде.
- Правильно управлять ключами шифрования.

Что проверять:

- Передаются ли данные через HTTPS?
- Не возвращается ли пароль в API Response?
- Не попадают ли токены и секреты в логи?
- Защищены ли чувствительные данные при хранении?

### A05. Injection — внедрение вредоносного кода

**Суть:** приложение воспринимает пользовательский ввод как исполняемые команды или код.

Основные разновидности:

- SQL Injection — внедрение SQL-команд.
- XSS — внедрение JavaScript.
- Command Injection — выполнение системных команд.
- LDAP Injection — внедрение LDAP-запросов.

<details>
  <summary>Пример SQL Injection</summary>

Приложение формирует запрос к базе данных напрямую из пользовательского ввода.

Злоумышленник вводит специальный SQL-фрагмент, который изменяет логику запроса.

</details>

Как защищаться:

- Использовать Prepared Statements.
- Применять параметризованные SQL-запросы.
- Проверять и валидировать входные данные.
- Экранировать вывод в зависимости от контекста.
- Не выполнять пользовательский ввод как системную команду.

Что проверять:

- Как приложение обрабатывает специальные символы?
- Можно ли изменить SQL-запрос через поля ввода?
- Может ли введённый HTML/JavaScript выполниться в браузере?
- Корректно ли валидируются входные параметры API?

### A06. Insecure Design — небезопасное проектирование

**Суть:** проблема заложена в архитектуре и бизнес-логике приложения ещё до написания кода.

<details>
  <summary>Пример</summary>

Интернет-магазин позволяет пользователю самостоятельно передавать цену товара через API.

```json
{
  "product_id": 123,
  "price": 1
}
```

Пользователь меняет цену товара с 1000 на 1.

Если сервер доверяет переданной цене, возникает уязвимость бизнес-логики.

</details>

Как защищаться:

- Проводить Threat Modeling.
- Проверять бизнес-логику.
- Рассчитывать критичные значения на сервере.
- Проектировать ограничения для критичных операций.
- Использовать принцип минимальных привилегий.

Что проверять:

- Можно ли обойти бизнес-правила?
- Можно ли изменить стоимость заказа?
- Можно ли повторно применить скидку?
- Можно ли совершить операцию несколько раз вместо одного?

### A07. Authentication Failures — ошибки аутентификации

**Суть:** приложение неправильно проверяет личность пользователя.

Примеры:

- Можно подобрать пароль без ограничений.
- Можно использовать украденный токен.
- Не завершается сессия после выхода.
- Можно обойти двухфакторную аутентификацию.
- Небезопасно реализовано восстановление пароля.

Как защищаться:

- Использовать MFA (многофакторную аутентификацию).
- Внедрять защиту от brute-force.
- Использовать безопасные механизмы управления сессиями.
- Устанавливать срок действия токенов.
- Безопасно реализовывать восстановление пароля.
- Хранить пароли в виде стойких хешей.

Что проверять:

- Есть ли ограничение количества попыток входа?
- Истекает ли токен?
- Инвалидируется ли сессия после Logout?
- Можно ли повторно использовать старый токен?
- Можно ли обойти MFA?

<hr />

### A08. Software or Data Integrity Failures — нарушение целостности ПО и данных

**Суть:** приложение доверяет данным или программным компонентам, подлинность и целостность которых не проверены.

Примеры:

- Использование неподписанных обновлений.
- Небезопасная десериализация объектов.
- Доверие данным из внешнего источника без проверки.
- Изменение критичных данных без проверки целостности.

Как защищаться:

- Проверять цифровые подписи.
- Проверять целостность загружаемых файлов.
- Использовать безопасную десериализацию.
- Контролировать источники данных.
- Проверять целостность обновлений.

Что проверять:

- Проверяет ли приложение подлинность обновлений?
- Можно ли подменить загружаемый файл?
- Проверяются ли входящие данные перед обработкой?

<hr />

### A09. Security Logging and Alerting Failures — недостатки логирования и оповещения

**Суть:** приложение не фиксирует важные события безопасности или не оповещает о подозрительной активности.

<details>
  <summary>Пример</summary>

Злоумышленник 100 раз пытается подобрать пароль, но система не записывает эти попытки и не создаёт предупреждений.

</details>

Как защищаться:

- Логировать неудачные попытки авторизации.
- Фиксировать изменения прав доступа.
- Записывать важные административные действия.
- Настраивать мониторинг и оповещения.
- Не записывать пароли, токены и другие секреты в логи.

Что проверять:

- Записываются ли неудачные попытки входа?
- Фиксируются ли подозрительные действия?
- Можно ли обнаружить попытки подбора пароля?
- Не попадают ли конфиденциальные данные в логи?

<hr />

### A10. Mishandling of Exceptional Conditions — неправильная обработка исключительных ситуаций

**Суть:** приложение неправильно ведёт себя при ошибках, сбоях и нестандартных ситуациях.

<details>
  <summary>Пример</summary>

Платёжный сервис отправляет запрос в банк. Банк не отвечает. Приложение ошибочно считает платёж успешным и выдаёт товар пользователю.

Другой пример: при ошибке проверки прав доступа система разрешает операцию вместо отказа.

</details>

Как защищаться:

- Использовать принцип Fail Secure (при ошибке безопасно отказывать).
- Корректно обрабатывать исключения.
- Не раскрывать внутренние сведения об ошибках.
- Обеспечивать атомарность критичных операций.
- Предусматривать таймауты и безопасные механизмы повторных запросов.

Что проверять:

- Что происходит при недоступности сервера?
- Что происходит при таймауте платежа?
- Не выполняется ли операция дважды при повторном запросе?
- Не выдаёт ли система доступ при ошибке проверки прав?
- Корректно ли обрабатываются пустые и некорректные ответы?
