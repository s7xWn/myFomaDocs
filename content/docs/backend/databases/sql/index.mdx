**Реляционные базы данных (РБД)** — это способ хранить данные в виде связанных между собой **таблиц**. Основа большинства прикладных систем: интернет-магазины, банки, CRM, учётные системы и т. д.

Базовое понятие называется **отношение (relation)**. На практике мы видим его как обычную **таблицу**, но за привычными словами стоят точные термины:

- **Отношение (таблица)** — множество строк одинаковой структуры.
- **Столбцы (columns)** — характеристики объекта;
  - Атрибут (столбец) — именованное поле определённого типа.
- **Строки (rows)** — конкретные объекты;
  - Кортеж (строка, tuple) — одна запись, один «объект».
- Домен — множество допустимых значений атрибута (например, `integer`, `date`, `text`).

Для работы с реляционными БД используется SQL — Structured Query Language.

## Нормализация

Нормализация — набор принципов проектирования таблиц, который помогает избежать избыточности и аномалий данных.

> Каждая сущность должна храниться там, где ей место.

<details>
  <summary>Примеры</summary>

Например, не стоит хранить имя пользователя в каждой записи заказа:

```
orders
id | user_id | user_name
```

если имя уже есть в `users`.

Лучше:

```
users
id | name

orders
id | user_id
```

</details>

### 1НФ

Каждая ячейка содержит одно неделимое значение, а строки можно однозначно идентифицировать.

<hr />

### 2НФ

Каждый неключевой атрибут зависит от всего первичного ключа, а не от его части. Важный нюанс: это правило вообще имеет смысл только при составном (из нескольких столбцов) ключе. Если ключ один столбец — частичной зависимости быть не может, и 2НФ выполнена автоматически.

<details>
  <summary>Пример</summary>

Пусть ключ — (`order_id`, `product_id`), а в той же таблице лежит `product_name`. Подумаем: от чего зависит имя товара? Только от `product_id` — название не меняется от того, в каком заказе товар. Значит, `product_name` зависит от части ключа — это частичная зависимость, нарушение 2НФ. Решение — вынести товары в отдельную таблицу.

</details>

<hr />

### 3НФ

Неключевые поля не должны зависеть друг от друга.

## Денормализация

Денормализация — это намеренное добавление избыточности в базу данных, чтобы ускорить чтение данных или упростить запросы.

> Нормализация → убираем дублирование и разделяем данные. <br/>
> Денормализация → иногда возвращаем дублирование ради производительности.

Нормализация убирает дубли, но взамен добавляет джойны, а они стоят времени.
Поэтому в реальных системах иногда намеренно денормализуют: дублируют данные или хранят заранее посчитанные агрегаты ради скорости чтения.
Классический пример — колонка `orders.total`, в которой лежит сумма заказа, вместо того чтобы каждый раз складывать позиции запросом.

Это допустимо, но у такого решения есть цена: теперь ты сам отвечаешь за то, чтобы дубль не разъехался с правдой (через триггеры или код приложения).
На собесе ценят, когда человек понимает этот trade-off, а не отвечает «нормализую всегда» — взрослый ответ звучит как «нормализую по умолчанию, денормализую осознанно под нагрузку».

## Ограничения (constraints)

Это важно: БД не просто хранит данные, она может защищать их целостность.

Например:

- `PRIMARY KEY` — уникальный идентификатор;
- `UNIQUE` — значение не должно повторяться;
- `NOT NULL` — значение обязательно;
- `CHECK` — дополнительное условие.

## Ключи

Ключ — это атрибут или набор атрибутов, который однозначно определяет строку.

Аналогия для ключей:

- суперключ — точно уникально, но с запасом;
- `candidate` — минимально и уникально;
- primary key — тот `candidate`, который ты выбрал главным идентификатором.

<Callout>
**Естественный ключ** — это данные из предметной области (ИНН, email).

_Суррогатный_ — искусственный `id` (autoincrement, UUID), не несущий смысла. На практике для PK чаще берут суррогатный: он стабилен (не меняется, если человек сменил email), компактен и не зависит от бизнес-данных.

</Callout>
### <Info className="inline-block size-4"/> Суперключ

Суперключ = любой набор столбцов, который однозначно определяет строку.

Если **один столбец** уже гарантирует **уникальность**, добавление **других столбцов её не нарушает**.

> Суперключ = уникальность + возможно лишние столбцы.

<hr />

### <Info className="inline-block size-4"/> Candidate key / Потенциальный ключ

Это суперключ без лишних столбцов.

<hr />

### Primary Key / Первичный ключ

Первичный ключ уникально идентифицирует запись.

Он `NOT NULL` и уникален. В Postgres под него автоматически создаётся уникальный индекс.

Первичный ключ не является обязательным требованием для существования таблицы в реляционной БД. <br/>
Если у таблицы нет первичного ключа, то сама таблица не гарантирует уникальность строк.

<details>
  <summary>Примеры</summary>

```sql
CREATE TABLE logs (
    created_at TIMESTAMP,
    message TEXT
);
```

</details>

<hr />

### Foreign Key / Внешний ключ

Столбец, который ссылается на первичный ключ другой (или той же) таблицы. Он гарантирует ссылочную целостность: нельзя сослаться на несуществующую строку.
