## Тестирование

— это процесс проверки программного обеспечения с целью обнаружения дефектов и оценки того, соответствует ли продукт требованиям и ожиданиям пользователей.

Тестирование — это проверка программы, чтобы убедиться, что:

- она работает так, как задумано;
- выполняет требования;
- не содержит критических ошибок;
- удобна и безопасна для использования.

Важно понимать, что тестирование не доказывает отсутствие ошибок, а помогает выявить как можно больше дефектов до того, как продукт попадет к пользователям.

### Тестирование показывает наличие дефектов, а не их отсутствие

Его смысл в том, что успешное прохождение тестов не доказывает, что в программе нет ошибок. Оно лишь показывает, что в тех местах и при тех условиях, которые были проверены, дефекты не обнаружены.

**Что это значит для тестировщика?**

Тестировщик должен не искать подтверждение, что «всё работает», а искать условия, при которых система может сломаться.

<hr />

### Исчерпывающее тестирование невозможно

— означает, что невозможно проверить абсолютно все возможные варианты работы программы, поэтому тестирование всегда связано с выбором наиболее важных сценариев.

<hr />

### Раннее тестирование

— это принцип разработки программного обеспечения, согласно которому тестирование начинается как можно раньше в жизненном цикле проекта, а не только после завершения разработки.

<hr />

### Скопление дефектов

— означает, что большая часть дефектов обычно сосредоточена в небольшом количестве компонентов или участков системы.

Проще говоря: 20% модулей могут содержать 80% ошибок (это не строгий закон, а практическое наблюдение, связанное с принципом Парето).

<hr />

### Парадокс пестицида

> Если многократно выполнять один и тот же набор тестов, со временем он перестает находить новые дефекты.

Парадокс пестицида означает, что если постоянно использовать один и тот же набор тестов, его эффективность со временем снижается: он перестает находить новые дефекты. Поэтому тесты необходимо регулярно пересматривать, дополнять новыми сценариями и изменять в соответствии с развитием продукта.

:::tip[История]
Название взято из сельского хозяйства: если постоянно использовать один и тот же пестицид(химическая отрава), вредители постепенно вырабатывают к нему устойчивость.
:::

<hr />

### Тестирование зависит от контекста

— означает, что нет универсального набора тестов, методов и подходов, которые одинаково хорошо подходят для всех проектов. То, как нужно тестировать продукт, зависит от его назначения, рисков, пользователей, технологий и условий разработки.

<hr />

### Заблуждение об отсутствии ошибок

> Даже если программа не содержит найденных ошибок, это не означает, что она полезна, соответствует требованиям или вообще нужна пользователю.

Иными словами: отсутствие обнаруженных дефектов ≠ качество продукта.

## Уровни тестирования

В QA обычно говорят о 4 уровнях тестирования. Они отличаются тем, что именно мы тестируем и на каком уровне системы.

:::warning
Не путай уровни тестирования с видами/типами тестирования.

Уровни: `Unit → Integration → System → Acceptance` <br/>
Виды/типы: `Functional, Regression, Smoke, Performance, Security, Usability` и т. д.

То есть, например, регрессионное тестирование — это не уровень тестирования, а вид тестирования, который может выполняться на разных уровнях.
:::

### Unit testing — модульное тестирование

Проверяем отдельные маленькие части кода: функции, методы, классы.

> Обычно выполняют разработчики, хотя QA должен понимать этот уровень.

<hr />

### Integration Testing — интеграционное тестирование

Проверяем, как отдельные компоненты взаимодействуют между собой.

<details>
  <summary>Пример</summary>

```
Frontend → API → Database
```

Проверяем, что:

- API правильно передаёт данные в БД;
- сервис корректно получает ответ от другого сервиса;
- данные не теряются при взаимодействии компонентов.

</details>

<hr />

### System Testing — системное тестирование

Проверяем систему целиком как единый продукт. <br/>
Здесь QA проверяет систему с точки зрения требований и пользовательских сценариев.

<details>
  <summary>Пример</summary>

Например, интернет-магазин:

```
Регистрация
    ↓
Поиск товара
    ↓
Добавление в корзину
    ↓
Оплата
    ↓
Создание заказа
```

</details>

<hr />

### Acceptance Testing — приёмочное тестирование

Проверяем, соответствует ли продукт бизнес-требованиям и готов ли он к выпуску.

Частый вариант — UAT (User Acceptance Testing), когда продукт проверяют представители бизнеса или конечные пользователи.

<details>
  <summary>Пример</summary>

Например, заказчик говорит:

> Пользователь должен иметь возможность оплатить заказ картой и получить подтверждение на email.

Мы проверяем, что эта бизнес-функциональность действительно работает.

</details>

## Пирамида тестирования

Пирамида тестирования — это модель, которая показывает, каких тестов в проекте должно быть больше, а каких меньше, чтобы тестирование было быстрым, надёжным и недорогим.<br/>
Пирамида тестирования — это не просто классификация тестов. Это рекомендация о том, как распределять автоматизацию.

Чем ниже уровень — тем больше тестов. Чем выше — тем меньше.

```
            /\
           /  \
          / UI \          ← мало
         /------\
        / API /  \        ← средне
       /----------\
      / Unit-тесты \      ← много
     /______________\
```

### Основание - Unit-тесты

Проверяют маленькие части кода отдельно: функцию, класс, метод.

> Пишет разработчик

:::important

- очень быстрые;
- дешёвые в написании и запуске;
- легко найти место ошибки.

Поэтому их должно быть больше всего.
:::

<hr />

### Середина - Integration / API-тесты

Проверяют, как несколько компонентов работают вместе.

Они медленнее и сложнее unit-тестов, поэтому их обычно меньше.

<details>
  <summary>Примеры</summary>

```
Frontend → API → Backend → Database
```

Или API:

```
POST /users
→ пользователь создаётся в БД
→ API возвращает 201
```

</details>

<hr />

### Вершина - UI / E2E-тесты

Проверяют приложение глазами пользователя.

:::important

- медленные;
- более хрупкие;
- дорогие в поддержке;
- могут падать из-за изменений интерфейса.

Поэтому их должно быть меньше всего.
:::

## Тест-дизайн

[Тест-дизайн](./test-design) — это процесс проектирования тестов: определения, что именно проверять, какими данными, в каких условиях и какие результаты считать правильными.

> Тест-дизайн — это способ придумать хорошие тесты так, чтобы проверить максимум важного, не создавая тысячи бесполезных проверок.

## Требования

— это описание того, что должна делать система и какими свойствами она должна обладать, чтобы удовлетворить потребности заказчика и пользователей.

Требования делятся на несколько видов:

- Бизнес-требования — описывают цели бизнеса.
  - Пример: «Увеличить количество онлайн-заказов на 20%.»
- Пользовательские требования — описывают, что должен иметь возможность делать пользователь.
  - Пример: «Пользователь может оформить заказ через мобильное приложение.»
- Функциональные требования — описывают функции системы.
  - Пример: «Система должна отправлять письмо с подтверждением после оформления заказа.»
- Нефункциональные требования — описывают характеристики качества.
  - Примеры:
    - время отклика не более 2 секунд;
    - доступность 99,9%;
    - поддержка 10 000 одновременных пользователей.

## Чек-лист тестирования требований

— это список критериев, по которым проверяют качество требований до начала разработки.

| Критерий                         | Что проверяем                                                     |
| -------------------------------- | ----------------------------------------------------------------- |
| ✅ Полнота                       | Все необходимые требования описаны?                               |
| ✅ Однозначность                 | Требование нельзя понять по-разному?                              |
| ✅ Непротиворечивость            | Нет ли конфликтов с другими требованиями?                         |
| ✅ Проверяемость (тестируемость) | Можно ли проверить выполнение требования?                         |
| ✅ Реализуемость                 | Можно ли технически реализовать?                                  |
| ✅ Актуальность                  | Требование действительно нужно?                                   |
| ✅ Прослеживаемость              | Есть связь с бизнес-целью, задачей или пользовательской историей? |
| ✅ Приоритет                     | Указана важность (Must, Should, Could и т.п.)?                    |
| ✅ Понятность                    | Требование написано простым и ясным языком?                       |
| ✅ Атомарность                   | Одно требование описывает одну функцию или условие?               |

## Верификация и валидация

| Верификация (Verification)                                                 | Валидация (Validation)                                                             |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Делаем ли мы продукт правильно?**                                        | **Делаем ли мы правильный продукт?**                                               |
| Проверяет соответствие требованиям, спецификациям и документации.          | Проверяет, удовлетворяет ли продукт потребности пользователя.                      |
| Ориентирована на процесс разработки.                                       | Ориентирована на конечный результат.                                               |
| Обычно выполняется без запуска программы (но не всегда).                   | Обычно выполняется с запуском программы.                                           |
| Примеры: ревью требований, ревью кода, анализ дизайна, статический анализ. | Примеры: функциональное, интеграционное, системное, приемочное (UAT) тестирование. |

**Верификация**

Цель — убедиться, что продукт разрабатывается в соответствии с требованиями.

**Валидация**

Цель — убедиться, что готовый продукт решает задачу пользователя.

> Верификация — проверка соответствия продукта требованиям и спецификациям. <br/>
> Валидация — подтверждение того, что продукт удовлетворяет потребности пользователя и решает поставленную задачу.

## Среды (окружения)

### Dev (Development)

**Dev** — среда разработки.

**Здесь работают разработчики**:

- пишут новый код;
- исправляют ошибки;
- добавляют новые функции;
- проводят первичные проверки.

**Особенности**:

- приложение может работать нестабильно;
- возможны частые изменения;
- данные часто тестовые.

**Кто работает**: разработчики, иногда QA.

**Пример**: разработчик добавил новую кнопку «Оплатить» и проверяет, что она вообще открывается.

### QA (Quality Assurance / Test)

**QA (или Test)** — среда тестирования.

После завершения разработки изменения попадают сюда, где их проверяют тестировщики.

**На QA**:

- выполняют ручное и автоматизированное тестирование;
- проверяют новые функции;
- ищут баги;
- создают баг-репорты.

**Особенности**:

- используются тестовые пользователи и данные;
- приложение уже намного стабильнее, чем на Dev.

**Кто работает**: QA-инженеры, иногда разработчики.

**Пример**: тестировщик оформляет заказ разными способами и проверяет, что всё работает корректно.

### Stage (Staging)

**Stage (Staging)** — это среда, максимально похожая на рабочую (Production).

Её задача — убедиться, что приложение готово к выпуску.

**На Stage**:

- проводят финальное тестирование;
- проверяют работу всей системы целиком;
- убеждаются, что обновление можно безопасно выпускать.

**Особенности**:

- конфигурация почти такая же, как в Production;
- часто используется копия базы данных (обычно обезличенная).

**Кто работает**: QA, разработчики, иногда заказчики или менеджеры.

**Пример**: перед релизом интернет-магазина проверяют регистрацию, вход, оплату, доставку и возвраты.

### Prod (Production)

**Production (Prod)** — это рабочая среда.

Именно здесь приложением пользуются реальные пользователи.

**Особенности**:

- доступны настоящие пользователи;
- используются реальные данные;
- любые ошибки могут повлиять на клиентов и бизнес.

**Кто работает**: пользователи, служба поддержки, DevOps, разработчики (при необходимости).

**Пример**: вы заходите в интернет-магазин и оформляете настоящий заказ — это работа в Production.

## Качество

— это степень, в которой программный продукт отвечает тем характеристикам и значениям пользователя, которые мы в него заложили.

### Атрибуты качества

Чтобы оценить степень готовности программы и ее соответствие требованиям и ожиданиям пользователей, выделяют несколько основных атрибутов качества.

1. Функциональность (Functionality).
   - Достаточно ли задач и целей решается с помощью существующих функций, упрощается ли процесс их решения и корректно ли они решаются с помощью функциональности программы.
2. Удобство использования (Usability).
   - Пользователи должны легко понимать, полезен ли им продукт. Они не должны рисковать, когда используют продукт, а сам продукт должен быть прост в использовании.
3. Эффективность (Performance Efficiency).
   - Как много ресурсов требуется программе для выполнения своих задач?
4. Надежность (Reliability).
   - Способность программного продукта функционировать при заданных условиях на протяжении определенного периода или для определенного количества операций.
5. Безопасность (Security).
   - То, как сильно рискуют пользователи своими личными данными, когда работают с программой.
6. Гибкость (Flexibility).
   - Способность программного продукта быстро и легко адаптироваться к изменениям в требованиях бизнеса или пользователя без значительных изменений в коде или функциональности.
7. Совместимость (Compatibility).
   - Этот атрибут описывает способность системы общаться с другими системами и обмениваться данными.
8. Поддерживаемость (Maintainability).
   - Удобство и объем работ сопровождения, в которых нуждается продукт. Чем сложнее вносить в программу изменения, тем хуже поддерживаемость.
9. Переносимость (Portability).
   - Способность сохранять работоспособность при переносе программы из одного окружения в другое.
10. Доступность (Availability).
    - Это способность программного обеспечения быть доступным для использования в любое время и в любом месте с минимальными задержками и проблемами. Часто выражается в процентах.

## Матрица трассируемости (Traceability Matrix)

— это таблица, которая показывает связь между требованиями → тест-кейсами → результатами тестирования.

> Она отвечает на вопрос «Каждое ли требование мы проверили тестами?»

Часто матрица имеет примерно такую структуру: <br/>
Requirement → User Story → Test Case → Bug → Test Result

**Traceability Matrix** — это по сути «карта связей» между требованиями и тестированием.

<hr />

### Пример

| ID требования | Требование                            | Test Case      | Результат |
| ------------- | ------------------------------------- | -------------- | --------- |
| REQ-001       | Пользователь может зарегистрироваться | TC-001, TC-002 | Passed    |
| REQ-002       | Пользователь может войти              | TC-003, TC-004 | Passed    |
| REQ-003       | Можно восстановить пароль             | TC-005         | Failed    |
| REQ-004       | Пароль должен быть минимум 8 символов | TC-006         | Passed    |

## Тестовые документации

— это набор документов, которые описывают, что, как и когда нужно проверять в программном продукте, а также фиксируют результаты тестирования.

**Зачем нужна тестовая документация?**

1. **Сохраняет знания**

   Если тестировщик уходит из проекта, новый специалист может быстро понять процесс.

2. **Делает тестирование системным**

   Без документации легко забыть важные проверки или тестировать хаотично.

3. **Упрощает работу команды**

   Разработчики, аналитики, менеджеры и тестировщики понимают, что именно проверяется.

4. **Помогает повторять проверки**

   Например, при каждом новом релизе можно снова выполнить один и тот же набор тестов.

5. **Позволяет оценивать качество продукта**

   По отчётам можно понять, насколько система готова к выпуску.
