---
title: Тест-дизайн (Test Design)
---

— это процесс проектирования тестов: определения, что именно проверять, какими данными, в каких условиях и какие результаты считать правильными.

> Тест-дизайн — это способ придумать хорошие тесты так, чтобы проверить максимум важного, не создавая тысячи бесполезных проверок.

Тестировщик не просто пишет тест-кейсы, а сначала выбирает, какие значения наиболее эффективно проверят поведение системы.

<details>
  <summary>Примеры</summary>

Допустим, есть поле «Возраст», куда разрешено вводить от `18` до `100`. <br/>
Можно просто: вести `25` → должно пройти.

Но хороший тест-дизайн заставит нас подумать о границах и классах эквивалентности:

| Значение | Что проверяем             | Ожидаемый результат |
| -------- | ------------------------- | ------------------- |
| 17       | ниже границы              | ошибка              |
| 18       | нижняя граница            | успешно             |
| 19       | чуть выше границы         | успешно             |
| 50       | обычное значение          | успешно             |
| 99       | чуть ниже верхней границы | успешно             |
| 100      | верхняя граница           | успешно             |
| 101      | выше границы              | ошибка              |
| `abc`    | текст                     | ошибка              |
| пусто    | отсутствие значения       | ошибка              |

</details>

## Основные техники тест-дизайна

### Классы эквивалентности (Equivalence Partitioning)

Делим входные данные на группы, внутри которых система должна вести себя одинаково.

### Анализ граничных значений (Boundary Value Analysis)

Проверяем значения на границах и рядом с ними.

### Таблица решений (Decision Table)

Используем, когда результат зависит от нескольких условий.

### Переходы состояний (State Transition)

Проверяем, как система ведёт себя при переходе из одного состояния в другое.

### Попарное тестирование (Pairwise Testing)

Используем, когда много параметров и комбинаций, чтобы проверить наиболее важные пары взаимодействий без полного перебора.

### Use Case / сценарный подход

Проверяем реальные пользовательские сценарии: например, «пользователь зарегистрировался → вошёл → оформил заказ».
